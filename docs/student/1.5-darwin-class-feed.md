# Student 1.5 – Darwin class feed (optional)

**Time:** 15 minutes · **Previous:** [Student 1.4](1.4-connect-to-the-class-feed.md) · **Next:** [Lab 2.1](../build/2.1-kql-transformations.md)

> **Optional, and only if your instructor runs it.** Do this page only if your handout has a row called
> **Optional Darwin feed (Student 1.5)**. Part 2 (Labs 2.1–2.10) works without Darwin: it's built on `TrustMovements` from
> Student 1.4. Darwin adds a few extra dashboard tiles (Lab 2.3) and data agent questions (Lab 2.4).

> ⚠️ **Capacity.** This adds a **third** always-on Eventstream to your workspace (as an **estimate**, about 1 CU more), and
> Darwin is much busier than TRUST. If your instructor asks you to, deactivate `RailEventstreamDarwin` when you're not
> using it: open it → **Deactivate all**. **Activate all** turns it back on, and it catches up from the Event Hub.

## Objectives

* Add **Darwin** forecasts, actual times and platforms for each service and calling point, alongside the TRUST movements
  from Student 1.4.
* Read them from the class Event Hub `rdm-darwin`, which your instructor fills from the Rail Data Marketplace Darwin feed.
  You don't need your own Darwin subscription.
* Keep Darwin in its **own** Eventstream, `RailEventstreamDarwin`, and its own raw table, **`RdmDarwinRaw`**. Update policies
  parse it into **`DarwinLocations`**.

Why a separate Eventstream? All the sources in an Eventstream feed one stream, so an extra source on `RailEventstreamRdm`
would send TRUST **and** Darwin messages into `RdmTrustRaw`.

## Before you start

* [Student 1.4](1.4-connect-to-the-class-feed.md) works: `RdmTrustRaw` gets rows.

  If it's missing, run `01_tables.kql` and then `02_update_policies.kql` again ([Student 1.2](1.2-fabric-workspace.md#create-the-raw-tables-and-mappings-now)).

## D1. Darwin feed → `RdmDarwinRaw`

Do the same as Student 1.4 S1, in **RailEventstreamDarwin**:

1. Open **RailEventstreamDarwin** → **Edit** → **Add source** → **Connect data sources** → **Azure Event Hubs** → **Connect**.
2. **Choose feature level**: **Extended features** for workspace identity (**Basic** only if your handout gives a key). Select **New connection**: a connection is tied to one event
   hub, so the ones from Student 1.4 won't work here.
   * **Event Hub namespace**: the namespace from the handout. **Event Hub**: `rdm-darwin`.
   * **Connection name**: `rail-rdm-darwin`.
   * **Authentication kind**: **Workspace identity** → **Connect** (or **Shared Access Key** if your handout gives a key).
     The instructor's read access covers every hub in the namespace, so there's nothing new to send.
3. **Consumer group**: **your own**, the same name as in Student 1.4 (for example `student07`). Never `$Default`.
4. **Data format**: **JSON** → **Next** → **Add**.
5. **Add destination** → **Eventhouse** → **Direct ingestion** → `RailEventhouse` / **`RailKQL`** → **Save** → **Publish**.
6. In **Live view**, select **Configure** on the Eventhouse node. Choose the **existing** table **`RdmDarwinRaw`** (not
   *New table*), format **JSON**, and the **existing mapping** **`RdmDarwinRawMapping`** → **Finish**. The preview should show
   one column, `payload`.

## How it's parsed

The same as for solo builders ([Solo 1.5 – How it's parsed](../solo/1.5-darwin-push-port.md#how-its-parsed)): the update
policy on `DarwinLocations` reads every new batch in `RdmDarwinRaw`, removes the RDM envelope with `UnwrapRdmDarwin()`, and
writes **one row per service (`rid`) and location (`tiploc`)** with planned, estimated and actual times, delays and platforms.
Lab 2.1 adds the query functions `DarwinLatest()`, `DarwinUnconfirmedPlatforms()` and `DarwinBiggestDelays()`.

> Darwin times are **UK local time** strings (`HH:MM` or `HH:MM:SS`) on the schedule start date (`ssd`), not UTC datetimes.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `rdm-darwin` isn't in the list of event hubs, or the connection says the hub doesn't exist | Your instructor hasn't turned on the Darwin class feed | Skip this page. It's optional |
| `RdmDarwinRaw` stays empty, but the source shows no errors | The instructor's Darwin relay isn't running yet, or another Eventstream uses your consumer group | Ask the instructor to check the Darwin relay. Check nobody else uses your consumer group on `rdm-darwin` |
| **Failed to publish changes** … *Required property 'type' not found in JSON*, or the preview shows NROD or TRUST messages | A schema problem with **Extended features**, or the source uses a connection for another hub | See [Student 1.4 – Troubleshooting](1.4-connect-to-the-class-feed.md#troubleshooting) |
| Source shows an authorisation error | The same causes as in Student 1.4 | See [Student 1.4 – Troubleshooting](1.4-connect-to-the-class-feed.md#troubleshooting) |
| Darwin rows are in `RdmTrustRaw` | The `rdm-darwin` source was added to `RailEventstreamRdm` instead of `RailEventstreamDarwin` | Delete that source from `RailEventstreamRdm` → **Publish**, add it to `RailEventstreamDarwin`. Then clear the wrong rows: `.clear table RdmTrustRaw data` |
| `DarwinLocations` empty although `RdmDarwinRaw` fills | The update policy is missing | Run `.show table DarwinLocations policy update`: `Source` must be `RdmDarwinRaw`. If not, re-run `01_tables.kql` then `02_update_policies.kql` |
| Your capacity is throttled | Three always-on Eventstreams in every student workspace | Deactivate `RailEventstreamDarwin` when you're not using it, and tell the instructor |
