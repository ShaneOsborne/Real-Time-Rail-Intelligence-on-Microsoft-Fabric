# Instructor 1.5 – Student workspaces, Foundry access and the handout

**Time:** 30 minutes · **Previous:** [Instructor 1.4](1.4-shared-event-hub.md) · **Next:** [Instructor 1.6](1.6-running-the-class.md)

## 1. Student workspaces (optional but recommended)

Either let students create their own in [Student 1.2](../student/1.2-fabric-workspace.md) (they need permission to assign
workspaces to the capacity: *Capacity settings → Contributor permissions*), or create them for them:

```bash
# One workspace per student, with the empty items; then add the student as Admin in the portal (Manage access)
for n in 01 02 03; do
  FABRIC_WORKSPACE_ID= FABRIC_WORKSPACE_NAME="rail-rti-student$n" ./scripts/fabric-setup.sh
done
```

Variables set on the command line win over `.env`. Note each workspace ID for the handout.

Set **workspace-level surge protection** limits on each student workspace, so one student can't starve the others
([classroom sizing](1.4-shared-event-hub.md#classroom-sizing-fabric-capacity)).

## 2. Consumer groups

Each student needs **their own** consumer group on every hub (`student01`, `student02` …), including `rdm-darwin` if you
run the [Darwin class feed](1.4-shared-event-hub.md#optional-darwin-class-feed). `create-eventhub` made them in
Instructor 1.4. To add more, see [Instructor 1.4, Option A step 3](1.4-shared-event-hub.md#option-a--automated-instructor).

## 2a. Workspace identity (only with `EVENTHUB_AUTH=entra`)

If you created the hub with `EVENTHUB_AUTH=entra` ([Key sign-in blocked by policy?](1.4-shared-event-hub.md#key-sign-in-blocked-by-policy-eventhub_authentra)),
there's no key to share. Each workspace reads the hub with its own **workspace identity** instead.

> **Check before the class:** students need the **Admin** role on their workspace to enable workspace identity. If you
> pre-created the workspaces in step 1, add them as **Admin**, or enable it for them.

1. Each student opens their workspace → **Workspace settings** → **Workspace identity** → enables it, and sends you the
   **ID** shown there (not the **App ID**).
2. You give each workspace identity the **Azure Event Hubs Data Receiver** role on the namespace:

   ```bash
   ./scripts/grant-eventhub-reader.sh --id <student01 ID> --id <student02 ID>
   # PowerShell: ./scripts/grant-eventhub-reader.ps1 -Id '<student01 ID>','<student02 ID>'
   ```

   The script shows each identity's name next to its ID, so you can check it matches the student's workspace.
   (It doesn't accept workspace names: they aren't unique in Entra ID.)

   It's safe to re-run. You need **Owner** or **User Access Administrator** on the namespace. A new role can take a few
   minutes to apply.
3. Tell each student when their workspace is done, so they can connect in [Student 1.4](../student/1.4-connect-to-the-class-feed.md).

Doing the dry run (step 6) with the same steps catches missing permissions early.

## 3. Foundry access for students

In the shared Foundry project (Instructor 1.1):

* Give every student **Foundry User**.
* Adding the **Fabric IQ** tool creates a project connection and needs **Foundry Project Manager**. Either give students that
  role, or add the tool for each student's data agent yourself (Lab 2.6, step 3).
* Each student uses **their own** agent name, for example `rail-network-agent-student07`, so agents don't clash in the shared project.

## 4. Azure Maps for Lab 2.9 (optional)

If the class does the optional [Lab 2.9](../build/2.9-azure-maps.md):

1. Do Lab 2.9 **steps 1–2** once for the class (or once per student): the Azure Maps account, and the railway-lines file
   committed to the repo. Add each student's app URL to `AZURE_MAPS_ALLOWED_ORIGINS`.
2. Each day of the class, create a token with `./scripts/new-azure-maps-sas.sh` (Lab 2.9, step 4) and give it to the
   students. It expires within 24 hours. Students do steps 3–6 with it.

## 5. The student handout

Send each student their own copy, **privately** (not in a repo, Teams channel or slide).

### Create every handout with one script

```bash
./scripts/make-handouts.sh --notes "Lab 2.5: yes. Lab 2.8: yes"
# PowerShell: ./scripts/make-handouts.ps1 -Notes 'Lab 2.5: yes. Lab 2.8: yes'
```

It writes one file per student, `handouts/student01.md`, `handouts/student02.md` …, plus `handouts/index.csv` (student,
workspace, workspace ID, agent name). Each file has the student's details, the `.env` lines to paste in Student 1.1, and the
Eventstream source settings for Student 1.4. It works out everything it can:

* **Students:** one handout for each `student01`, `student02` … consumer group it finds on the hub. Use `--students 1-12` (or
  `3,7`) for some of them only.
* **Workspace name:** `rail-rti-` + the consumer group, as in step 1. Change it with `--workspace-prefix` or
  `STUDENT_WORKSPACE_PREFIX` in `.env`. If the workspace already exists and you can see it, its ID is filled in too.
* **Event Hubs:** the namespace, and with key sign-in the `students-listen` key. If the `rdm-darwin` hub exists, an
  *Optional Darwin feed (Student 1.5)* row too. With `EVENTHUB_AUTH=entra` it writes the
  workspace identity steps instead of a key.
* **Foundry:** `FOUNDRY_PROJECT_ENDPOINT` and `FOUNDRY_MODEL_DEPLOYMENT_NAME` from your `.env`, and an agent name per student
  (`rail-network-agent-student07`).
* **Reference Lakehouse:** your `FABRIC_WORKSPACE_NAME` and `FABRIC_LAKEHOUSE_NAME`. Use `--reference-workspace` if it's in
  another workspace.
* **Labs 2.5 and 2.8:** whatever you pass in `--notes` (from Instructor 1.1). Without it, students are told to ask you.
* **Azure Maps (optional):** `--maps` creates today's token (Lab 2.9, step 4) and adds it. Or pass one with `--maps-token`.

Anything it can't find is shown as *[ask the instructor]* and named in a warning, so check the warnings before you send.
The `handouts/` folder is git-ignored because it can contain the key. Delete it after the class.

### What's in the handout

| Item | Example | From |
|---|---|---|
| Fabric workspace name (and ID if you pre-created it) | `rail-rti-student07` | Step 1 |
| Event Hubs namespace | `railrti-eh-xxxx` | `create-eventhub` output (Instructor 1.4) |
| Key name and key (key sign-in only) | `students-listen` / `…` | `create-eventhub` output (Listen only) |
| **Their** consumer group | `student07` | Step 2 |
| Reference Lakehouse | workspace `rail-instructor` → `RailLakehouse` → `Tables/locations` | Instructor 1.2 |
| Foundry project endpoint and model deployment | `https://…/api/projects/…`, `gpt-5.4` | Foundry portal |
| Their agent name | `rail-network-agent-student07` | Step 3 (unique per student in the shared project) |
| Whether Lab 2.5 (ontology) and Lab 2.8 (Fabric Apps) work in your tenant and region | "Lab 2.5: yes. Lab 2.8: yes" | Instructor 1.1 |
| Azure Maps token (optional, Lab 2.9) | `eyJ…` (valid 24 hours) | Step 4 |

The values go into the student's `.env` as shown in [Student 1.1](../student/1.1-get-ready.md#settings-for-your-env).
The Event Hubs key goes into the Eventstream source in the portal, not into `.env`.

**Handout variant for `EVENTHUB_AUTH=entra`.** Replace the *Key name and key* row with these two rows. There's no key in
this handout:

| Item | Example | From |
|---|---|---|
| Authentication kind | **Workspace identity** (no key) | Instructor 1.4 |
| Before connecting | Enable workspace identity, send the **ID** shown there (not the App ID) to the instructor, and wait for confirmation | Step 2a |

Everything else in the handout stays the same.

- [ ] The dry run reached the Student 1.4 checkpoint
