# Solo 1.7 – Deploy the bridge to Azure Container Apps

**Time:** 30 minutes · **Previous:** [Solo 1.6](1.6-bridge-local.md) · **Next:** [Solo 1.8](1.8-shared-event-hub.md) (optional) or [Lab 2.1](../build/2.1-kql-transformations.md)

## Objectives

* Host the bridge 24×7 on **Azure Container Apps**, with **exactly one replica** (min = max = 1) at **0.25 vCPU / 0.5 GiB**.
* Keep secrets in **Key Vault**, read through a **user-assigned managed identity**, and send logs to **Log Analytics**.
  (If your subscription blocks public access to Key Vault, use `SECRETS_SOURCE=inline` – see [below](#if-your-subscription-blocks-public-access-to-key-vault).)
* Build the image in **Azure Container Registry**, or use a public **GHCR** image built by CI.
* *Optional:* point the bridge at the shared **Azure Event Hub** (`BRIDGE_TARGET=eventhub`) and deploy the **RDM Kafka relay** as a second app (`DEPLOY_RDM_RELAY=true`). See [Solo 1.8](1.8-shared-event-hub.md).

Cost: about **$14/month** list-price estimate after the free grant, plus small Log Analytics, Key Vault and ACR charges. For `TD_ALL_SIG_AREA`, set `BRIDGE_CPU=0.5` and `BRIDGE_MEMORY=1Gi`.

## Prerequisites

* The bridge works locally with the eventstream sink (Solo 1.6), and `EVENTSTREAM_CONNECTION_STRING` is in `.env`.
* `AZ_RESOURCE_GROUP`, `AZ_LOCATION` (for example `uksouth`, close to your Fabric capacity) and `NAME_PREFIX` are set in `.env`.
* **Stop the local bridge** (one connection per NROD account / client-id).
* `NROD_TOPICS=RTPPM_ALL` in `.env` (the same feeds as Solo 1.6). The deployment copies it into the container app. Don't add `TRAIN_MVT_ALL_TOC` if Solo 1.4 already brings in Train Movements.
* If you created the shared Key Vault in [Solo 1.1, step 8](1.1-prerequisites.md#8-shared-key-vault-for-credentials-needed-from-solo-13), keep the
  same `AZ_RESOURCE_GROUP` and `NAME_PREFIX` (and `KEY_VAULT_NAME`, if you set it). This lab then **re-uses that vault** and just adds the
  `eventstream-connection-string` secret. If you skipped that step, the vault is created here.

## Option A – automated

```bash
az login
./scripts/deploy-bridge.sh --what-if     # optional preview
./scripts/deploy-bridge.sh               # or: ./scripts/deploy-bridge.ps1
```

What it does:
1. Phase 1 Bicep (`deployApp=false`) creates the identity, Log Analytics, Key Vault (or re-uses the one from Solo 1.1), ACR (unless `CONTAINER_IMAGE` is set) and the Container Apps environment.
2. Writes `nrod-username`, `nrod-password` and `eventstream-connection-string` to Key Vault, retrying while RBAC propagates.
3. Runs `az acr build`, so you don't need Docker locally.
4. Phase 2 Bicep (`deployApp=true`) deploys the container app with Key Vault secret references, probes on `/healthz` and 1 replica.

### If your subscription blocks public access to Key Vault

By default the Container App reads its secrets through **Key Vault references**: at deploy time and on every restart,
Container Apps fetches them from the vault's **public endpoint** using the managed identity. Many corporate subscriptions
(including Microsoft internal ones) have an Azure Policy that turns public access off or adds a vault firewall, so phase 2
fails with:

```
Invalid value: "nrod-password": Unable to get value using Managed identity …/railrti-bridge-id for secret nrod-password
```

Check the vault (replace the name):

```bash
az keyvault show -n <vault> --query "{public:properties.publicNetworkAccess, firewall:properties.networkAcls.defaultAction}"
```

`public: Disabled` or `firewall: Deny` confirms it. Writing secrets from your own machine can still work (your network
may be allowed), which is why phase 1 succeeds.

**Fix for the lab:** store the secrets as **Container Apps secrets** instead. They're encrypted at rest and only visible to
people with access to the app, but they live in the app rather than in Key Vault, and you update them by re-running the
script.

```bash
SECRETS_SOURCE=inline ./scripts/deploy-bridge.sh          # PowerShell: $env:SECRETS_SOURCE='inline'; ./scripts/deploy-bridge.ps1
```

The script reads the values from `.env` and passes them in a temporary parameters file that it deletes afterwards. To keep
it for every run, add `SECRETS_SOURCE=inline` to `.env`.

The production-grade alternative keeps Key Vault and adds a **private endpoint**, with the Container Apps environment in
a virtual network. That's out of scope for this lab.

### Optional: shared Event Hub target and RDM relay (Solo 1.8)

Run `./scripts/create-eventhub.sh` (or `.ps1`) first. It writes `eventhub-nrod-connection-string` and `eventhub-rdm-connection-string` to the shared Key Vault. Then:

| Variable (`.env` or shell) | Default | Effect |
|---|---|---|
| `BRIDGE_TARGET` | `eventstream` | `eventhub`: the bridge app uses the Key Vault secret `eventhub-nrod-connection-string`, `EVENTHUB_CONNECTION_STRING` and `BRIDGE_SINK=eventhub`. `EVENTSTREAM_CONNECTION_STRING` isn't needed |
| `DEPLOY_RDM_RELAY` | `false` | `true`: also stores `rdm-kafka-username` / `rdm-kafka-password` and deploys `<NAME_PREFIX>-rdm-relay` (same image, `BRIDGE_SOURCE=kafka`, 1 replica, 0.25 vCPU / 0.5 GiB). Needs `RDM_KAFKA_*` in `.env` |

```bash
BRIDGE_TARGET=eventhub DEPLOY_RDM_RELAY=true ./scripts/deploy-bridge.sh
```

The script stops early if a required Event Hub secret is missing. The Bicep parameters are `bridgeTarget` and `deployRdmRelay` (plus
`rdmKafkaBootstrapServers`, `rdmKafkaTopic` and `rdmKafkaConsumerGroup`). With the defaults, the deployment is exactly the same as before.
Setting `DEPLOY_RDM_RELAY=false` later doesn't delete an existing relay app (deployments are incremental):
`az containerapp delete -g $RG -n ${NAME_PREFIX:-railrti}-rdm-relay --yes`.

To use the image built by GitHub Actions instead (`.github/workflows/bridge-ci.yml` pushes it to GHCR), make the package public or add registry credentials, then set:

```bash
CONTAINER_IMAGE=ghcr.io/<owner>/rail-fabric-rti-bridge:latest
```

Use your GitHub user or organisation name in lowercase (for example `ghcr.io/shaneosborne/...`). Image names can't contain capital letters.

## Option B – manual

### B1. Infrastructure (portal or CLI)

```bash
RG=rg-rail-fabric-rti; LOC=uksouth
az group create -n $RG -l $LOC
ME=$(az ad signed-in-user show --query id -o tsv)
az deployment group create -g $RG -n bridge-phase1 -f infra/main.bicep -p @infra/main.parameters.json \
  -p deployApp=false deployerPrincipalId=$ME   # add keyVaultName=<name> if you created the vault by hand in Solo 1.1
KV=$(az deployment group show -g $RG -n bridge-phase1 --query properties.outputs.keyVaultName.value -o tsv)
ACR=$(az deployment group show -g $RG -n bridge-phase1 --query properties.outputs.acrName.value -o tsv)
```

To do it in the portal instead, create the same resources: a *Managed identity*, a *Log Analytics workspace*, a *Key Vault* (RBAC mode; grant yourself
*Key Vault Secrets Officer* and the identity *Key Vault Secrets User* – if you already created the vault in Solo 1.1, just add the identity's role), a *Container registry* (Basic; grant the identity *AcrPull*) and a
*Container Apps environment* (Consumption) with **Logging options → Azure Monitor**, then **Diagnostic settings → Add** sending
*Container App console logs* and *system logs* to the Log Analytics workspace.

### B2. Secrets

Pick **one** of the two ways – the same choice as `SECRETS_SOURCE` in Option A
([why](#if-your-subscription-blocks-public-access-to-key-vault)).

**Key Vault (default).** Store the secrets in the vault; the app reads them with its managed identity:

```bash
# Skip these two if you already stored them in Solo 1.1:
az keyvault secret set --vault-name $KV -n nrod-username --value "<NROD email>"
az keyvault secret set --vault-name $KV -n nrod-password --value "<NROD password>"
az keyvault secret set --vault-name $KV -n eventstream-connection-string --value "<Endpoint=sb://...>"
```

Typing secrets on the command line can leave them in your shell history. Use the portal (*Key Vault → Secrets → Generate/Import*) if you'd rather avoid that.

**Inline (Container Apps secrets).** Use this if a policy blocks public access to your Key Vault. Skip the commands above:
the values go straight into the container app in B4. Load them into your shell without typing them on the command line:

```bash
set -a; source .env; set +a                 # .env must quote values with $ ; or & (see Solo 1.6)
read -rsp "NROD password: " NROD_PASSWORD; echo   # optional: type it instead of reading it from .env
```

### B3. Image

```bash
az acr build -r $ACR -t rail-bridge:v1 src/bridge
```

### B4. Container app

**Key Vault (default):**

```bash
az deployment group create -g $RG -n bridge-phase2 -f infra/main.bicep -p @infra/main.parameters.json \
  -p deployApp=true imageTag=v1 deployerPrincipalId=$ME
```

**Inline (Container Apps secrets):**

```bash
az deployment group create -g $RG -n bridge-phase2 -f infra/main.bicep -p @infra/main.parameters.json \
  -p deployApp=true imageTag=v1 deployerPrincipalId=$ME secretsSource=inline \
     nrodUsernameValue="$NROD_USERNAME" nrodPasswordValue="$NROD_PASSWORD" \
     bridgeConnectionStringValue="$EVENTSTREAM_CONNECTION_STRING"
```

The values come from shell variables, so they don't land in your shell history, but they're briefly visible to other
processes on your machine while the command runs (Option A avoids that with a temporary parameters file). A value that
starts with `@` would be read as a file name by `az`: use Option A in that case.

In the portal, you'd create a *Container App* with: image `<acr>.azurecr.io/rail-bridge:v1` pulled with the managed identity;
**0.25 CPU / 0.5 Gi**; **Scale min 1 / max 1**; ingress **disabled**; secrets as **Key Vault references** (identity = the UAMI) –
or, for the inline choice, **Secrets → + Add → Type: Container Apps secret** with the value pasted in;
environment variables `BRIDGE_SINK=eventstream`, `BRIDGE_SOURCE=stomp`, `NROD_TOPICS=…`, and `NROD_USERNAME`, `NROD_PASSWORD` and `EVENTSTREAM_CONNECTION_STRING` → *Reference a secret*;
and a liveness probe of HTTP GET `/healthz` on port 8080. For the optional shared Event Hub, the portal steps for the bridge and the
RDM relay app are in [Instructor 1.4, B6](../instructor/1.4-shared-event-hub.md#b6-container-apps).

## Checkpoint

```bash
APP=${NAME_PREFIX:-railrti}-bridge
az containerapp replica list -g $RG -n $APP -o table          # exactly 1 replica
az containerapp logs show -g $RG -n $APP --follow --format text
```

You should see `stomp connected`, then `subscribed`. After that the bridge is quiet: it doesn't log each message, but it
writes a `status` line every 5 minutes with its counters (`frames_received`, `events_sent`, `frames_acked`). *No logs since
last 60 seconds* between them is normal.

In Log Analytics (the `railrti-logs` workspace, or the Container Apps environment → **Logs**):

```kusto
ContainerAppConsoleLogs
| where ContainerAppName endswith "-bridge"
| project TimeGenerated, Log
| order by TimeGenerated desc
| take 50
```

The environment sends logs through **Azure Monitor** (a diagnostic setting on the environment) into the
`ContainerAppConsoleLogs` and `ContainerAppSystemLogs` tables. Older guides use `ContainerAppConsoleLogs_CL`, from the
previous *Log Analytics* destination, whose ingestion API reached end of support on 14 September 2026, so this lab
doesn't use it.

**The table doesn't exist yet?** Log Analytics only creates it when the first log line arrives, and a new diagnostic
setting can take **up to 90 minutes** to start sending. Until then, use `az containerapp logs show` above, which streams
directly from the app. If there's still nothing after 90 minutes, check the environment → **Monitoring → Logging
options** shows *Azure Monitor*, and **Monitoring → Diagnostic settings** sends *Container App console logs* to
`railrti-logs`.

In Fabric, `RawFeed | summarize max(received_utc)` should advance every few seconds.

## Troubleshooting

| Symptom | Fix |
|---|---|
| No `ContainerAppConsoleLogs` (or `ContainerAppConsoleLogs_CL`) table, but `az containerapp logs show` and `RawFeed` show data | The environment was deployed with the older *Log Analytics* destination, which writes `_CL` tables through an API that reached end of support on 14 September 2026 (and fails where a policy disables workspace shared keys). Re-run `deploy-bridge` – the template now uses Azure Monitor with a diagnostic setting – or switch by hand: `az containerapp env update -g $RG -n <prefix>-env --logs-destination azure-monitor`, then `az monitor diagnostic-settings create --name <prefix>-env-logs --resource $(az containerapp env show -g $RG -n <prefix>-env --query id -o tsv) --workspace $(az monitor log-analytics workspace show -g $RG -n <prefix>-logs --query id -o tsv) --logs '[{"category":"ContainerAppConsoleLogs","enabled":true},{"category":"ContainerAppSystemLogs","enabled":true}]'`. Allow up to 90 minutes, then query `ContainerAppConsoleLogs` |
| `az monitor diagnostic-settings create` fails in Git Bash with `usage error: --resource ID \| --resource NAME ...` | Git Bash rewrites arguments that start with `/` (such as Azure resource IDs) into Windows paths, and `az ... -o tsv` output can end with a hidden `\r` | Run the commands with path conversion turned off and strip the carriage return: `export MSYS_NO_PATHCONV=1`, then `ENV_ID=$(az containerapp env show -g $RG -n <prefix>-env --query id -o tsv \| tr -d '\r')` and `LAW_ID=$(az monitor log-analytics workspace show -g $RG -n <prefix>-logs --query id -o tsv \| tr -d '\r')`, then `az monitor diagnostic-settings create --name <prefix>-env-logs --resource "$ENV_ID" --workspace "$LAW_ID" --logs '[{"category":"ContainerAppConsoleLogs","enabled":true},{"category":"ContainerAppSystemLogs","enabled":true}]'`. Or run it from PowerShell |
| Phase 2 fails: **`Unable to get value using Managed identity … for secret nrod-password`** (or `nrod-username`) | Container Apps can't read the vault. Usually a policy has turned off the vault's public access or added a firewall: see [If your subscription blocks public access to Key Vault](#if-your-subscription-blocks-public-access-to-key-vault) and re-run with `SECRETS_SOURCE=inline`. Less often the role assignment is still propagating – the script already retries for about 3 minutes |
| `--what-if` shows **`~ Microsoft.KeyVault/vaults/…` `publicNetworkAccess: "Disabled" => "Enabled"`**, or the deployment fails with **`RequestDisallowedByPolicy`** on the Key Vault, or the app logs a Key Vault secret error | An Azure Policy in your organisation turns off public network access on Key Vaults (common in corporate subscriptions). The Container App reads its secrets from Key Vault over the public endpoint, so it needs it on. Check: `az keyvault show -n <vault> --query properties.publicNetworkAccess` and `az policy state list --resource <vault-id> --filter "complianceState eq 'NonCompliant'" --query "[].policyDefinitionName"`. If the policy only **audits** or **modifies**, deploying turns access back on, but a *modify* policy may switch it off again later. If it **denies**, ask your subscription owner for an exemption for this lab vault, or use a subscription without the policy |
| Logs show **`AMQ339009 Exception getting session`** | Usually a temporary NROD block after too many connection attempts, or a second connection on the same account (for example a local Solo 1.6 bridge). Stop the local bridge; the Container App waits 25 minutes by itself after this error and then reconnects. Full checklist in [Solo 1.6 troubleshooting](1.6-bridge-local.md#troubleshooting) |
| Phase 2 fails with a Key Vault reference error | RBAC propagation can take a few minutes. The script retries. Re-run it if needed |
| `ImagePullBackOff` / unauthorized | The identity is missing *AcrPull*, or the GHCR image is private |
| App restarts repeatedly | Check the logs for NROD login errors. Make sure no local bridge uses the same client-id |
| Replica count shows 0 | `minReplicas` must be 1. Re-deploy phase 2 |
| CPU throttling with TD | Increase to `0.5` vCPU / `1Gi` |
| Rotating the Eventstream key | Update the Key Vault secret, then `az containerapp revision restart` (or deploy a new revision) |
| `Key Vault secret 'eventhub-…' not found` | `BRIDGE_TARGET=eventhub` or `DEPLOY_RDM_RELAY=true` without the shared Event Hub | Run `./scripts/create-eventhub.sh` first (Solo 1.8) |
| Relay restarts with SASL errors | Wrong RDM credentials in Key Vault | Update `rdm-kafka-username` / `rdm-kafka-password`, then restart the relay revision |
